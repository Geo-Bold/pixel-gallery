Preface

Early in my education, while I was still making buttons change colors and learning about time complexities, I desired to obtain a consistent system for measuring my own progress. Initially, I determined that the more I could implement from memory, the more developed I was becoming. With the advent of AI, I began to measure my progress by the number of technologies I could learn or features I could build. If an application worked and the interface looked polished, I considered it complete. This all changed over the last two years of my professional experience building the ProcECS Engine. It was here that I began to appreciate the sheer scale of building production software, maintaining existing systems, and studying how large-scale applications are designed; I realized that writing code is only a small part of engineering. The more difficult questions revolve around preserving data integrity, designing clear system boundaries, understanding tradeoffs, and building software that remains correct as requirements evolve.

That shift in perspective is what led to Qrum. The project began as a university capstone intended to help a local organization manage its own volunteering events. Events were tracked manually via a disconnected network of spreadsheets and word documents that easily became outdated and were cumbersome to propagate, both internally and to its network of external volunteers. While the original goal was to create a functional application, I saw it as an opportunity to continue exploring the engineering problems that had become increasingly interesting to me. Rather than treating it as an intellectual exercise, I decided to incorporate it into a personal case study where I could experiment with architectural decisions that are common in production systems but often absent from classroom projects.

Each new feature was introduced to solve a specific problem encountered during development. Authorization evolved beyond UI checks into a layered security model backed by PostgreSQL Row-Level Security. Event management became a system of explicit lifecycle transitions protected by database invariants instead of simple CRUD operations. Search progressed from straightforward SQL queries to measured comparisons between PostgreSQL Full-Text Search and Elasticsearch before introducing a change-data-capture pipeline to keep search infrastructure separate from transactional writes. Along the way I added structured logging, observability, deployment automation, and operational tooling--not because the technologies themselves were the goal, but because each addressed a concrete limitation uncovered in discussions with the client and limitations in previous iterations.

This document follows that progression. Rather than presenting the final architecture in isolation, it explains how the system evolved, why each decision was made, the alternatives that were considered, and the tradeoffs that shaped the final design. My goal is two-fold; I wish to show the reasoning process behind building a system whose complexity grew only when the problem demanded it as well as create a permanent record, for myself and others, to appreciate the hundreds of hours committed to solving an engineering problem that I can hopefully someday look back upon fondly.

Overview

Qrum is a volunteer management and event-discovery platform. It was built directly with a nonprofit running volunteer programs. During conversations with staff and coordinators, we realized that events were being managed and tracked by hand: a sign-up spreadsheet, a separate form for new events, a group chat or mass emails for changes, and no reliable way to answer basic questions about who was confirmed, whether an event was actually full, or what had changed since last week.

After several conversations with the client, we determined that this was less of a technology gap than a domain-modeling one. General purpose tools were being asked to represent things they were never built to hold: event lifecycles, capacity limits, roster changes that should show history, and information that's public for some people and sensitive for others. Volunteers, who need to find something worth showing up for nearby and soon, and staff, who need to trust that what the system tells them is actually true, were both underserved by the same underlying gap.

Three groups use the resulting system day to day: volunteers browsing and enrolling, staff coordinators creating and managing events and rosters, and administrators with oversight into history the other two don't need.

The approach throughout was to treat these as system invariants, not screens the interface had to display correctly. This case study follows the project in the order its limitations actually appeared, starting from a plain data model that worked at first, through each specific gap that made it insufficient and finally to the decision that closed it.

The Problem

Every gap on both sides traces back to the same root: the tools in use had no concept of the domain they were being asked to manage. A spreadsheet doesn't know what an event actually is. It doesn't know an event has a capacity, a state it moves through, or a history worth keeping. It just holds rows. What follows isn't a list of missing features. It's what that absence actually costs the two groups living with it every day.

Volunteers

A person interested in volunteering is really asking a narrow question: what's happening near me, soon, that I'd actually want to do? A spreadsheet or a bare list of every event the organization has ever run doesn't answer that. Requiring a user to call and inquire or having a member of staff log into a system and track down a spreadsheet isn't productive or pleasant. The observer is required to do the filtering themselves. Sorting by nothing in particular, searching by hand, and hoping the address in row 214 is still accurate is homework, not discovery. It fails in smaller ways too. Misspelled search terms return nothing, an event two states away sits right next to one down the street with no distinction, and there's no way to know whether "full" is current or three days stale.

None of that is a user's fault. It's the predictable result of using a tool with no concept of geography, recency, or relevance, any of which it was never built to have.

Staff

Failures on the staff side tend to be more painful. A spreadsheet does not know an event has a fixed number of slots, so it will happily record the twenty-first sign-up for a twenty-person shift, and the coordinator only finds out when twenty-five people show up on Saturday. It can not distinguish a draft event a coordinator is still writing from one that has actually been published, so an unfinished listing goes live, or a live one gets edited with no warning to anyone already signed up. It has no real notion of history either. If a start time changes the week of the event, there is often no record of who changed it, when, or what it said before. And a shared sheet holding volunteer names, phone numbers, and addresses is exactly that, shared, whether or not everyone with access to it should have it.

Individually these look like small operational nuisances. Across a volunteer program running many events with turnover in both staff and volunteers, they can start to add real risk: overcommitted events, silent data loss, and no accountability for what changed.
